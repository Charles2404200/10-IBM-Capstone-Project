## 1. What changed from version 1

The first frontend draft was written before Anubhav's plan existed. It asked
seventeen open questions and assumed the smallest possible feature: a single
WebSocket subscription, no persistence, no history. His design is larger and
answers most of those questions, so this version realigns rather than argues.

Four substantive corrections:

| v1 said | Now |
|---|---|
| WebSocket only | WebSocket **and** three REST integrations (§5) |
| One subscription destination | One channel per role, derived from the signed-in user's role |
| Contract is `{ topic, message }` | Insufficient — read tracking and de-duplication need a stable id (§6) |
| "A WebSocket cannot deliver messages generated while offline, and this plan does not assume persistence" | Wrong for this design. Persistence is the system of record and offline recovery is required (Backend §5.1, §5.3) |

One finding from v1 is retained unchanged, and matters more under this design
than it did before: §7.

## 2. Agreed design (backend — Anubhav)

Summarised for alignment only.

- **Role-targeted, administrator-initiated.** An administrator composes a
  notification for one or more of the four roles. Notifications are not
  generated by domain events, and are not addressed to individual users
  *(Backend §2, §4.1)*.
- **Four roles**, matching the existing `UserRole` enum exactly — verified:
  `LEARNER`, `SCENARIO_AUTHOR`, `REVIEWER`, `ADMINISTRATOR`.
- **Persistence first, delivery second.** The notification is written to the
  database before real-time delivery is attempted. The database is the system
  of record; WebSocket is immediate delivery on top of it *(Backend §5.1)*.
- **A separate WebSocket channel per role**, with authorisation enforced at
  both connection and subscription level, so knowing another role's destination
  does not grant access *(Backend §3.1, §3.3)*.
- **Kafka** between creation and processing, with producer retries, a consumer,
  retry classification, a dead-letter topic, concurrency and failover
  *(Backend §4)*.
- **Per-user read state.** One role notification is visible to many users, each
  with an independent read status and an idempotent acknowledgement
  *(Backend §6.1, §6.3)*.
- **Offline and reconnection recovery**, which Anubhav's plan explicitly
  assigns to both sides *(Backend §5.3, §5.4)*.

### Infrastructure note, for scheduling only

Kafka appears in `docker-compose.yml` behind the `extended` profile, but no
backend source file uses it today. It is new infrastructure rather than
existing infrastructure being reused. Recorded because the frontend integration
work cannot begin until the consumer → WebSocket path runs end to end; it is
not a comment on the design, which is Anubhav's call.

## 3. Frontend objective

Follow the backend design with the smallest client that satisfies it:

1. Keep one authenticated STOMP connection open for the signed-in user.
2. Subscribe to the channel for that user's role.
3. Treat the WebSocket as the *fast path* and the REST history as the *truth*,
   because the backend does — anything else would let the two disagree.

## 5. Frontend architecture

The correction that matters most from v1: this is two transports, not one.

```text
  LOGIN
    │
    ├─ REST  GET /api/v1/notifications ───────────► history for my role
    │                                               + my read state
    │                                               (the source of truth)
    │
    └─ STOMP CONNECT  /ws   (JWT in CONNECT headers)
             │
             └─ SUBSCRIBE  <role channel — exact string TBC, Q2>
                      │
                      │   administrator creates a notification
                      │   → Kafka → consumer → database → push
                      ▼
                 MESSAGE frame ──► merge into the same store,
                                    de-duplicated by id

  RECONNECT ──► re-subscribe ──► re-fetch history (a push may have been
                                  missed while the socket was down)

  USER OPENS ONE ──► POST acknowledgement ──► update read state
```

### Why history is re-fetched on reconnect

The socket delivers only to a connected subscriber. Anything published while it
was down is not replayed. Because the backend keeps the durable record
*(Backend §5.1)*, the client recovers by asking for history again rather than
by trying to make the socket reliable *(Backend §5.4)*.

### Two things both called "topic"

Unrelated, and still unresolved — see Q1.

| Term | Meaning |
|---|---|
| **STOMP destination** | The channel address, chosen and authorised by the backend |
| **`topic` field in the payload** | A value inside the JSON — probably a title |

## 6. Message contract

**PROVISIONAL — REQUIRES ANUBHAV'S CONFIRMATION.**

The `{ topic, message }` shape originally described cannot support this design.
Read tracking needs to identify a notification, duplicate suppression needs the
same identity *(Backend §5.2)*, and a list needs an order. Proposed minimum:

```ts
interface Notification {
  /** Stable identity. Required for read state and de-duplication. */
  id: string
  /** Target role. */
  role: 'LEARNER' | 'SCENARIO_AUTHOR' | 'REVIEWER' | 'ADMINISTRATOR'
  /** Meaning unconfirmed — assumed to be the title. See Q1. */
  topic: string
  /** Body text. */
  message: string
  /** ISO-8601. Ordering and display. */
  createdAt: string
  /** This user's state, not a global one (Backend §6.1). */
  read: boolean
}
```

The same shape should come back from the history endpoint and over the socket,
so one parser and one store serve both. If they differ, that difference needs
to be deliberate and documented.

Unknown fields will be ignored rather than rejected, so the backend can add
fields without breaking the client.

## 7. Security finding — carried over from v1, still open

Verified in `MeetingSubscriptionInterceptor.preSend`:

```java
Matcher matcher = destination != null ? MEETING_TOPIC.matcher(destination) : null;
if (matcher == null || !matcher.matches()) {
    // Not a per-meeting topic (or malformed) — nothing for this interceptor to authorize.
    return message;
}
```

Only destinations matching `^/topic/meetings/([0-9a-fA-F-]{36})$` are
authorised. **Everything else is explicitly allowed through.**

Anubhav's §3.3 requires role authorisation at subscription level, which is the
right requirement. The point of raising it here is narrower: that authorisation
**must be added**; the existing interceptor cannot be relied on, because its
default for an unrecognised destination is to permit. Until a notification
interceptor exists, any authenticated user can subscribe to any role's channel
and read notifications intended for administrators.

This is the failure mode of per-role topics generally: they fail open. The
alternative — Spring user destinations — fails closed, but does not fit
role-targeted fan-out, and would additionally require `/queue` to be added to
`enableSimpleBroker("/topic")`. Role topics under `/topic` work with the broker
exactly as configured today, so the current configuration is the right one for
this design.

The frontend cannot mitigate any of this.

## 8. Lifecycle and error handling

| Case | Frontend behaviour |
|---|---|
| Not signed in | Do not connect |
| Server unavailable | `stompjs` retries every `reconnectDelay`; the app works without notifications |
| STOMP error | `onStompError` — log, do not blank the page |
| Unauthorised subscription | Surfaces as a STOMP error; do not retry blindly |
| Connection closed | `onWebSocketClose`; automatic reconnect follows |
| Reconnected | Re-subscribe **and** re-fetch history (F4) |
| Malformed JSON | `try`/`catch` around the parse; drop the frame. An uncaught throw inside a STOMP callback can take down the app |
| Missing required field | Validate before use; drop or fall back |
| Duplicate delivery | De-duplicate by `id`. Kafka redelivery is expected *(Backend §5.2)*, so the client must not assume exactly-once |
| History fetch fails | Keep whatever is already in the store; retry via react-query |
| Token expires mid-connection | **Undecided — Q3.** The JWT is validated only at `CONNECT`, so an open socket keeps working |
| Logout / unmount | `deactivate()`, clear the store |

### Exactly one connection

Two hazards. React StrictMode double-invokes effects in development, so an
`activate()` without correct cleanup opens two sockets. And because
notifications are app-wide rather than page-scoped, the client belongs at a
single mount point near `AppShell` rather than in every component that reads
notifications. Reading the token through `useAuthStore.getState().token` rather
than as a subscribed value keeps the effect from re-running on unrelated store
changes — the pattern `useMeetingSocket` already uses.

## 9. Reuse of existing conventions

`apps/web/src/api/hooks/useMeetingSocket.ts` already establishes all of this,
and the notification client will follow it rather than invent alternatives:
`@stomp/stompjs` (already a dependency), `/ws` derived from
`VITE_API_BASE_URL`, `Authorization: Bearer <jwt>` in the `CONNECT` frame,
`reconnectDelay: 3000`, 10-second heartbeats, `onStompError` /
`onWebSocketClose`, and `deactivate()` on cleanup.

The JWT travels in the STOMP `CONNECT` frame because a browser cannot attach a
custom `Authorization` header to a WebSocket handshake. It must never be put in
the URL, where it would reach server logs, proxy logs and browser history.

**No second WebSocket endpoint.** One socket carries many subscriptions; a
second endpoint means a second handshake and a second copy of the
authentication logic. `WebSocketConfig`'s own Javadoc anticipates this,
proposing that the transport and auth interceptor move to `shared.config` once
a second feature needs them. Notifications are that feature — recorded as a
backend recommendation, not actioned here.

## 10. Notification UI — proposed, not approved

`AppShell.tsx` already renders a Carbon `<HeaderGlobalBar>` containing one
`<HeaderGlobalAction>` (sign out). A notification control would sit beside it.

Anubhav's design implies more than a toast: per-user read state and a
retrievable history only mean something if there is a list to read them in. On
that basis the realistic minimum is a bell with an unread count and a panel.

| Option | Fits the backend design? |
|---|---|
| Toast only | No — nothing would use read state or history |
| Bell + unread badge + panel | Yes, minimum viable |
| Full notification centre page | Yes, more than currently justified |
| Admin creation + read-status screens | Required by Backend §2 and §6.4 — **owner unassigned, Q4** |

Whichever is chosen, a notification that exists only as a colour or a silent
toast is invisible to a screen reader; an `aria-live` region is the minimum.
